# Тестирование A2A

## Кроссплатформенные Python-скрипты для тестирования

В дистрибутив входят Python-скрипты для тестирования. Для них нужен
Python 3.10 или новее.

Проверить, что внешний A2A endpoint доступен, и вывести Agent Card:

```shell
python test_external_a2a.py --base-url https://ailab.se.ifmo.ru/
```

Создать произвольную задачу и дождаться первого содержательного статуса:

```shell
python test_a2a_status.py \
  --base-url http://ailab.se.ifmo.ru/ \
  --prompt "Подготовь связь с реактором и построй план. Не запускай эксперимент."
```

Чтобы универсальный скрипт подтвердил готовый план и дождался успешного
завершения задачи, добавьте `--approve`. Перед подтверждением потребуется
ввести `RUN`:

```shell
python test_a2a_status.py --base-url http://ailab.se.ifmo.ru/ --prompt "ВАШ ЗАПРОС" --approve
```

Для контролируемого автоматического теста ручной ввод отключается комбинацией
`--approve --yes`. В этом режиме код `0` возвращается только при
`TASK_STATE_COMPLETED`; ошибка возвращает `1`, новый запрос ввода — `2`.

Для полного актуального сценария по химии используется отдельный скрипт:

```shell
python test_reactor_experiment_a2a.py \
  --base-url http://ailab.se.ifmo.ru/
```

Без дополнительных флагов он создает уникальную задачу, ждет окончания
планирования, печатает все ответы A2A и безопасно останавливается, когда план
переходит в `TASK_STATE_INPUT_REQUIRED/approval`. Это проверяет доступность
роутера, агента, MCP-каталога и построение полного плана, но не запускает
оборудование.

После проверки плана разрешить выполнение на реальном оборудовании:

```shell
python test_reactor_experiment_a2a.py \
  --base-url http://ailab.se.ifmo.ru/ \
  --approve
```

Перед отправкой подтверждения скрипт потребует вручную ввести `RUN`. Флаг
`--approve --yes` отключает эту последнюю защиту и предназначен только для
контролируемого автоматического теста. После подтверждения скрипт продолжает
опрашивать задачу до завершения, ошибки или нового запроса ввода.

Каждый запуск формирует новые `experiment_id`, `contextId`, `messageId`,
поэтому не должен попадать под дедупликацию предыдущего эксперимента. Если
агент запросил дополнительные параметры (`waiting_input`) либо не смог
сопоставить какой-либо шаг с методом MCP, скрипт ничего не выдумывает и
завершается с кодом `2`, оставляя полный ответ в консоли для диагностики.

## Информация по A2A взаимодействию с агентом A2A JSON-RPC


## 1. Получение возможностей

```json
{
  "jsonrpc": "2.0",
  "id": "capabilities-001",
  "method": "GetCapabilities",
  "params": {}
}
```

В `result` должны вернуться доступные агенты, оборудование и процедуры.
Перед тестом реального оборудования проверьте наличие нужного устройства и
процедуры.

## 2. Создание задачи

Для каждого нового эксперимента используйте новые `id`, `messageId`,
`contextId` и `experiment_id`.

```json
{
  "jsonrpc": "2.0",
  "id": "create-001",
  "method": "message/send",
  "params": {
    "message": {
      "messageId": "msg-create-001",
      "role": "ROLE_USER",
      "contextId": "ctx-exp-001",
      "parts": [
        {
          "text": "Подготовь эксперимент для выбранного устройства и построй план. Не запускай эксперимент."
        }
      ]
    },
    "metadata": {
      "experiment_id": "exp-001",
      "domain": "experiment-lab"
    }
  }
}
```

Чтобы план сразу дошел до подтверждения, укажите в тексте конкретное
устройство, процедуру и все обязательные параметры. Для другого устройства
меняется текст задания и уникальные идентификаторы.

Первый ответ должен содержать:

```text
TASK_STATE_SUBMITTED / submitted
```

Скопируйте `result.task.id`. Далее он обозначен как `TASK_ID`.

## 4. Проверка составления плана

Подставьте реальный `TASK_ID`:

```json
{
  "jsonrpc": "2.0",
  "id": "status-001",
  "method": "tasks/get",
  "params": {
    "id": "TASK_ID"
  }
}
```

Во время построения ожидается:

```text
TASK_STATE_WORKING / planning
```

Повторяйте запрос, меняя JSON-RPC `id` на `status-002`, `status-003` и далее.
Значение `TASK_ID` должно оставаться прежним.

## 5. Проверка запроса ввода или подтверждения

После планирования ожидается `TASK_STATE_INPUT_REQUIRED`. JSON-часть сообщения
уточняет причину:

- `"phase": "approval"` — план готов и ожидает подтверждения;
- `"phase": "waiting_input"` — не хватает параметров или уточнения.

Если получен `TASK_STATE_FAILED`, прочитайте `status.message.parts[0].text` и
JSON в следующей части. Это ошибка планирования, LLM, MCP или профилей, а не
ошибка Swagger.

## 6. Передача недостающих параметров

При `waiting_input` отправьте новый `messageId`, сохранив исходные `TASK_ID`,
`contextId` и `experiment_id`:

```json
{
  "jsonrpc": "2.0",
  "id": "clarification-001",
  "method": "message/send",
  "params": {
    "message": {
      "messageId": "msg-clarification-001",
      "role": "ROLE_USER",
      "taskId": "TASK_ID",
      "contextId": "ctx-exp-001",
      "parts": [
        {
          "text": "Здесь укажите запрошенные параметры. Обнови план, но не запускай его."
        }
      ]
    },
    "metadata": {
      "experiment_id": "exp-001",
      "domain": "experiment-lab"
    }
  }
}
```

После этого снова проверяйте статус через `tasks/get`.

## 7. Подтверждение плана

Выполняйте этот запрос только после проверки плана и только если разрешен
запуск оборудования:

```json
{
  "jsonrpc": "2.0",
  "id": "approval-001",
  "method": "message/send",
  "params": {
    "message": {
      "messageId": "msg-approval-001",
      "role": "ROLE_USER",
      "taskId": "TASK_ID",
      "contextId": "ctx-exp-001",
      "parts": [
        {
          "text": "Подтверждаю план. Запусти все шаги."
        }
      ]
    },
    "metadata": {
      "experiment_id": "exp-001",
      "domain": "experiment-lab"
    }
  }
}
```

После подтверждения вызывайте `tasks/get`, пока задача не перейдет в конечное
состояние.

## 8. Отмена

```json
{
  "jsonrpc": "2.0",
  "id": "cancel-001",
  "method": "tasks/cancel",
  "params": {
    "id": "TASK_ID"
  }
}
```

При аварии на реальном оборудовании используйте предусмотренный процесс
экстренной остановки, а не полагайтесь только на отмену A2A-задачи.

## 9. Ожидаемый результат

Успешный тест до подтверждения показывает цепочку:

```text
TASK_STATE_SUBMITTED / submitted
→ TASK_STATE_WORKING / planning
→ TASK_STATE_INPUT_REQUIRED / approval
```

Она подтверждает работу Swagger, A2A-роутера, агента, LLM, каталога процедур
и MCP-интеграции на этапе построения плана. Оборудование начинает исполняться
только после отдельного запроса из раздела 7.

## 10. Удаление сохранённых A2A-задач

Удалить одну завершённую задачу вместе с ключами дедупликации:

```json
{
  "jsonrpc": "2.0",
  "id": "delete-001",
  "method": "DeleteTask",
  "params": {
    "id": "TASK_ID"
  }
}
```

Удалить все неактивные задачи агента:

```json
{
  "jsonrpc": "2.0",
  "id": "clear-001",
  "method": "ClearTasks",
  "params": {}
}
```
