# CoScientist — профиль «Микрофлюидика»

Отдельная конфигурация CoScientist для кейса микрофлюидики: разработка
веществ (например, ПАВ) с получением целевых молекул на проточном /
микрофлюидном реакторе. Из полной системы оставлены только оркестратор с
планером и анализ литературы; добавлен агент постановки ТЗ, портированный из
проекта **VibePAV** (`VibePAV/`), и стадии 3–11 — от молекулярного дизайна до
финального отчёта.

## Пайплайн

Граф **модульный**: `RootOrchestrator` маршрутизирует только модули целиком и
никогда не заглядывает внутрь — границу пересекают ровно три ребра (2→3, 4→6,
7→11), остальные рёбра модуль разруливает сам. Каждый запрос в этом
деплойменте — кейс микрофлюидики, поэтому стадия ТЗ выполняется
детерминированно ПЕРЕД планированием:

```
запрос заказчика
  └─ RootOrchestrator (llm)                      маршрутизирует ТОЛЬКО модули
       ├─ ModuleA_TZLiterature (sequential)      стадии 1–2
       │    ├─ TZAgent (sequential)                        ← порт VibePAV
       │    │    ├─ TZSpecAgent      → state["structured_tz"]          таблица ТЗ
       │    │    └─ TZQueryGenAgent  → state["tz_literature_queries"]  LIT-01…LIT-06
       │    ├─ PlannerAgent          → create_plan: одна задача на каждый LIT-запрос
       │    └─ LiteratureOrchestrator→ делегирует LIT-задачи ResearchAgent
       ├─ ModuleB_Design (sequential)            стадии 3–5
       │    └─ MolDesignAgent → SynthRouteAgent → EconomicsAgent
       ├─ ModuleC_Experiment (sequential)        стадии 6–10
       │    ├─ ExpPlannerAgent
       │    └─ ExperimentLoop (loop, max_iterations=3)     цикл 7⇄8
       │         ├─ OptimizerAgent   → A2A-модуль оптимизации → CFD через его MCP
       │         └─ EquipmentAgent   → установка, журнал для следующей итерации
       └─ ReportAgent (llm)                      стадия 11 → final_report
```

> Оптимизация подключена через A2A; только внешний модуль оптимизации
> вызывает CFD. Установка пока использует `rig_mcp_stub`; её телеметрия
> не является физическим измерением. Остальные сервисы зависят от настроек
> соответствующих модулей.

- **TZSpecAgent** — превращает свободный запрос в структурированный
  **документ ТЗ** формата эталонного примера
  (`CoScientist/microfluidics/Пример_уточненного_структурированного_ТЗ_для_агентов.md`):
  16 канонических блоков (тип задачи, целевой продукт, область применения,
  требуемые свойства, критерии качества, масштаб, ограничения по
  сырью/поставкам/себестоимости/технологии, оборудование, аналитика, данные
  заказчика, безопасность, приоритеты, форма результата), каждый блок —
  таблица конкретных полей «Поле | Значение | Статус».
  Схема: `CoScientist/microfluidics/models.py::StructuredTZ` (блоки → поля);
  человекочитаемый Markdown-документ рендерится детерминированно
  (`render.py::render_tz_document`): правила интерпретации статусов, исходный
  запрос, обзорная таблица, таблицы блоков, незаполненные поля, проверка по
  опроснику. Документ сохраняется в `state["structured_tz_document"]` и в файл
  `tz_documents/TZ_<timestamp>.md`; в HITL-ревью оператор видит именно этот
  документ, а не JSON. После принятия ТЗ (перед переходом к планированию и
  поиску литературы) агент публикует документ в чат — сообщением с путём к
  файлу и полным текстом; открыть последний документ в браузере:
  `GET /api/tz-document` (конкретный файл — `?name=TZ_<timestamp>.md`).

  **ТЗ заполняется последовательно, по разделам** (`microfluidics/tz_builder.py`).
  Агент не отвечает готовым JSON: он вызывает тул `fill_tz_section(section,
  usage, fields)` — один вызов на один раздел, строго в каноническом порядке.
  Ответ тула — прогресс и следующий шаг: «Вы заполнили 3/16 … теперь вы должны
  заполнить раздел 4 «Требуемые свойства»» плюс рекомендуемые поля этого
  раздела. Отклонённый вызов ничего не сохраняет и указывает место ошибки:
  шаг, раздел, номер и имя поля, недопустимое значение и что допустимо
  (`Шаг 4/16, раздел «Требуемые свойства», поле №2 «ККМ (CMC)»: недопустимый
  статус «задан» …`). Проверяются порядок разделов, статусы, пустые значения
  при статусах «задано…/автоподбор/уточнено…/свободный комментарий», дубли имён, лишние
  ключи, usage; несколько вызовов в одном ответе — выполняется только первый.
  Тул сам пишет `state["structured_tz"]` (у агента нет `output_key`), исходный
  запрос берётся из сообщения пользователя дословно. Если агент завершил ход
  на полпути, `TZSessionAgent` возвращает его дозаполнять с нужного раздела
  (до 3 раз). Текстовые правки (консольный «Edit») запускают новую
  редакцию — ТЗ заполняется заново с раздела 1; правки из веб-формы вносятся
  точечно, без перезаполнения (см. «Панель ТЗ» ниже).

  **Параллельная сборка** (`options.parallel_build: true` в профиле, по
  умолчанию). 16 разделов разбиты на 3 независимые части — `SECTION_GROUPS`
  в `tz_builder.py`:

  | Часть | Разделы |
  |---|---|
  | «Задача и продукт» | Тип задачи, Целевой продукт, Область применения, Приоритеты отбора, Форма результата |
  | «Свойства и качество» | Требуемые свойства, Критерии качества, Масштаб результата, Аналитические методы |
  | «Ограничения и ресурсы» | Ограничения по сырью / поставкам / себестоимости / технологии, Доступное оборудование, Известные данные заказчика, Безопасность и регуляторика |

  Разделы с общим полем лежат в одной части, чтобы значение совпадало
  (минимальная масса образца — в «Критериях качества» и «Масштабе результата»;
  запрещённые вещества — в «Сырье» и «Безопасности»). `TZSpecAgent` запускает
  на каждую часть своего воркера (`TZSpecAgent_task`, `_quality`, `_limits`:
  та же модель, свой промпт, тот же контракт `fill_tz_section`, но только по
  разделам своей части) — **все одновременно**, вместо того чтобы одна LLM
  шла по 16 разделам подряд. Каждый воркер пишет в свой ключ
  `state["structured_tz_part_<часть>"]` и работает в своей ветке (branch): он
  видит запрос и правки оператора, но не ходы других воркеров. Когда воркеры
  закончили, части собираются в `state["structured_tz"]` в каноническом
  порядке. Упавший или не доделавший часть воркер перезапускается один — с
  того раздела, на котором остановился; текстовые правки пересобирают все
  части заново.

  Так же параллельно **дозаполняются поля, оставленные оператором пустыми**:
  запрос делится по частям (`state["structured_tz_agent_fill_<часть>"]`), и
  воркер каждой части, где есть такие поля (`TZSpecAgent_<часть>_fill`),
  заполняет их через свой `fill_agent_fields` — тоже по разделу за вызов, со
  статусом «заполнено агентом». Промпт воркера перестраивается перед каждым
  вызовом: в нём всё текущее ТЗ (включая значения оператора и других частей) и
  оставшиеся поля его части. Значения хранятся в доле части и попадают в
  `state["structured_tz"]`, когда воркеры закончили; панель ТЗ показывает их
  сразу. Ревью оператора и публикация документа остаются за самим
  `TZSpecAgent`. `parallel_build: false` возвращает последовательные сборку и
  дозаполнение собственной LLM агента.

  Для правки уже собранного ТЗ по разделам подготовлен тул
  `edit_tz_section(section, fields, usage='')` — заменяет таблицу одного
  раздела, остальные не трогает. Он зарегистрирован в `assembly/bindings.py`,
  но **пока не выдан ни одному агенту**.
- **TZQueryGenAgent** — из ТЗ формирует 4–6 точечных поисковых задач
  (`id`, `task`, `extract`) — это и есть структурированная информация о том,
  что именно запрашивать у агента анализа литературы. Поисковые запросы
  `ResearchAgent` составляет сам по формулировке задачи.
- **PlannerAgent** получает ТЗ и запросы через инъекции состояния
  (`{structured_tz?}`, `{tz_literature_queries?}`) и регистрирует план:
  одна задача на LIT-запрос, assignee `ResearchAgent`, `task` — дословно
  в описании задачи.
- **LiteratureOrchestrator** (бывший `OrchestratorAgent`, опущен внутрь
  модуля A) исполняет план, передавая задачу и список извлекаемых данных в
  `ResearchAgent` (websearch + papers_search + paper_analysis), затем сводит
  находки по структуре ТЗ.

### Стадии 3–11

Контракт по состоянию сессии — каждый узел пишет ключ, который читает
следующий; на этом и держатся рёбра графа:

| # | Агент | Читает | Пишет (`output_key`) |
|---|---|---|---|
| 3 | `MolDesignAgent` | `structured_tz`, `search_results` | `design_candidates` — SMILES + свойства |
| 4 | `SynthRouteAgent` | `design_candidates` | `synthesis_routes` — маршрут + условия операций |
| 5 | `EconomicsAgent` | `synthesis_routes` | `economics` — стоимость, доступность в РФ, риски |
| 6 | `ExpPlannerAgent` | `synthesis_routes` | `experiment_plan` — план опытов |
| 7 | `EquipmentAgent` | `experiment_plan` | `experiment_journal` — данные эксперимента |
| 8 | `OptimizerAgent` | ТЗ, маршруты, экономика, план, журнал | `experiment_plan`, `optimization_a2a_task`, `optimization_a2a_runs` |
| 11 | `ReportAgent` | всё вышеперечисленное | `final_report` |

- **Цикл 8→7→8**: сначала `OptimizerAgent` отправляет данные внешнему модулю
  через A2A, затем `EquipmentAgent` исполняет полученный план и дополняет журнал.
  Следующая итерация отправляет обновлённый журнал оптимизатору.
  `finish_optimization` завершает цикл; `max_iterations: 3` ограничивает число
  итераций. После последней итерации журнал попадает в отчёт; достижение
  оптимума из самого факта исчерпания лимита не следует.
- **Экономика передаётся в оптимизацию**: `economics_ranking` вместе с
  маршрутами, ТЗ и литературными данными входит в запрос A2A.
- **CFD отсутствует среди инструментов профиля**: ни `cfd_mcp`, ни его
  заглушка, ни общий MCP-набор `microfluidics` агенту установки не выдаются.
- **Проверка перед установкой**: callback `require_optimization_result`
  пропускает только новый результат завершённой A2A-задачи с содержимым.
  Проверка исполнимости самого плана и блокирующих результатов CFD остаётся
  обязанностью агентов и HITL: сервис не документирует структурную схему плана.
  Оба агента используют существующий механизм Work Order; установка также
  проверяет отдельные шаги.

### A2A-оптимизация: настройка и состояния

Адаптер: `CoScientist/microfluidics/a2a_optimization/adapter.py`.
Используется JSON-RPC-клиент из этой же папки: `message/send`, `tasks/get`,
`ROLE_USER`, metadata с `experiment_id` и `domain: experiment-lab`.

Адрес выбирается из `OPTIMIZATION_A2A_URL`, затем `A2A_ROUTER_PUBLIC_URL`;
по умолчанию — `http://127.0.0.1:19000/`, как в текущих локальных скриптах.
Для удалённого сервиса задайте его адрес явно через переменную окружения.
Для каждого HTTP-запроса установлен тайм-аут 30 секунд. Промпт ограничивает
ожидание 12 проверками с паузами по 5 секунд; сетевое время добавляется к паузам.

`optimization_start()` берёт входы из состояния сессии и сохраняет уникальные
`experiment_id`, `context_id`, `message_id`. Пока результат не передан установке,
повторный вызов не создаёт другую задачу. `optimization_get_status()` читает
сохранённый `task_id`. Все исходные ответы с artifacts и status.message остаются
в `optimization_a2a_runs` для отчёта.

`input_required` с фазой `approval` или `waiting_input` останавливает цикл и
передаётся в отчёт как запрос подтверждения/данных. Автоматической отправки
подтверждения в адаптере нет. Уточнение или подтверждение существующей задачи
передаётся оператором через интерфейс сервиса по контракту `A2A-TESTING.md`,
с исходными идентификаторами; после этого статус можно перечитать в той же
сессии. Если отправка завершилась неоднозначной ошибкой без `task_id`,
автоматическая повторная отправка заблокирована: сначала нужно выяснить исход
на стороне сервиса. Ошибка или ожидание никогда не обозначаются как успешная
оптимизация. Возможность выполнения CFD на удалённом сервере требует проверки
интеграционным тестом: в предоставленной документации описан транспорт и
планирование оборудования, но не отдельная схема результата оптимизации.

### Подготовленные тесты (не запускались при внесении изменения)

Автономные проверки графа, передачи экономики и журнала, идентификаторов,
сохранения результатов CFD, пауз/ошибок, защиты от повторной отправки и
изоляции сессий:

```bash
.venv/bin/python -m pytest tests/unit/test_microfluidics_optimization_a2a.py -q
```

Интеграционный тест использует тот же адаптер, что агент; по умолчанию пропущен.
Подготовьте JSON с реальными `synthesis_routes`, `experiment_plan` и при наличии
`structured_tz`, `literature_analysis`, `economics`, `economics_ranking`,
`experiment_journal`. Путь задаётся через `OPTIMIZATION_A2A_INPUT`:

```bash
RUN_OPTIMIZATION_A2A_TEST=1 OPTIMIZATION_A2A_INPUT=/path/input.json \
  .venv/bin/python -m pytest tests/integration/test_optimization_a2a.py -s -q
```

Тест отправляет запрос на планирование и опрашивает задачу, но не подтверждает
и не запускает установку. `completed` или `input_required` подтверждают обмен;
сам по себе этот тест не доказывает научную корректность оптимизации/CFD.

## Запуск отдельного инстанса

Профиль выбирается переменной окружения `COSCIENTIST_CONFIG`
(имя профиля → `CoScientist/agents/<имя>.yaml`, либо путь к YAML):

```bash
# веб-интерфейс на отдельном порту (по умолчанию 8010) — можно поднимать
# параллельно с основным CoScientist на 8000
python scripts/run_microfluidics_web.py

# без человека (headless-режим для тестирования — HITL полностью выключен)
python scripts/run_microfluidics_web.py --no-hitl

# или вручную:
COSCIENTIST_CONFIG=microfluidics COSCIENTIST_WEB_PORT=8010 python CoScientist/web/server.py

# валидация конфигурации (без LLM-вызовов)
COSCIENTIST_CONFIG=microfluidics python -m CoScientist.assembly
```

### Индикатор состояния — «Этап k из N»

Профиль объявляет `pipeline: linear: true`: корень запускает модули по
порядку, модуль — свои шаги по порядку. Поэтому индикатор состояния в
веб-интерфейсе показывает не очередной тул (в этом пайплайне они почти все
одинаковые — `fill_tz_section`, заглушки), а **этап**: «Этап 4 из 10 · Анализ
литературы», под ним — что делается внутри этапа, полоса — сколько этапов
пройдено. В развёрнутом виде — список всех этапов.

Этапы выводятся из конфига (`SystemConfig.linear_stages`): подчинённые корня
по порядку, sequential-модули раскрываются в свои шаги, выключенные шаги
выпадают; всё поддерево шага (его подчинённые, например `ResearchAgent` у
`LiteratureOrchestrator`, и агенты цикла) считается его этапом. Подпись этапа —
поле `title` агента. Список уходит в браузер в `session_snapshot`
(`pipeline_stages`); текущий этап индикатор определяет по событиям
`agent_start`/`agent_end` из `tool_activity` (воркеры `TZSpecAgent_<часть>`
относятся к этапу `TZSpecAgent` по префиксу имени). Этап считается пройденным,
когда закончил работу его собственный агент или начался следующий.

Те же этапы — это **план** в правой панели (`plan_tracker.js`): строка на этап
с его состоянием (ожидает / в работе / выполнен / ошибка), счётчик и полоса —
пройденные этапы. Задачи роадмапа (`LIT-01…` от `PlannerAgent`) вложены под
этап своего исполнителя — `ResearchAgent` входит в «Анализ литературы».
Список отдаёт индикатор (`StatusIndicator.stages()`) и перерисовывает панель,
когда меняется состояние какого-нибудь этапа. Без `pipeline.linear` панель
показывает только задачи роадмапа.

## Human-in-the-loop (ревью оператора)

Аналог интерактивного опросника VibePAV: обе стадии ТЗ и планер — session-агенты
с циклом ревью. Агент предлагает артефакт, человек одобряет или присылает
правки, агент переделывает до одобрения:

1. **TZSpecAgent** — ТЗ, раундами формы в панели ТЗ (см. ниже);
2. **TZQueryGenAgent** — литературные запросы LIT-xx;
3. **PlannerAgent** — план;
4. **LiteratureOrchestrator** — общий Work Order на весь этап анализа
   литературы: согласование плана поиска в начале и проверка сводного отчёта
   в конце (вызовы ResearchAgent по отдельным LIT-задачам выполняются
   автономно без частых остановок оператора).

В веб-UI запрос ревью — карточка в чате: заголовок, **текст предложения агента**
(документ ТЗ / JSON запросов, прокручиваемый блок), поле для правок и кнопки
**Accept** (принять как есть), **Revise** (отправить правки — агент перепишет
результат с их учётом) и **Reject**. Внимание: без ответа оператора запрос
авто-подтверждается через 5 минут (`WebHITLHandler.HITL_TIMEOUT_SECONDS`).
В CLI — консольное меню.

### Панель ТЗ — заполнение оператором и агентом

В навигации веб-UI на месте «Планировщика задач» — пункт **«Техническое
задание»** (`TZSpecAgent`). Панель показывает ТЗ по разделам **вживую**, пока
агент их заполняет: TZSpecAgent работает внутри AgentTool (своя дочерняя
сессия), поэтому после каждого изменения он сам отправляет снимок ТЗ
(`microfluidics/tz_live.py` → ws-событие `tz_snapshot`; последний снимок
отдаёт и `GET /api/users/{u}/sessions/{s}/tz`, и `session_snapshot` при
переподключении).

Когда все разделы заполнены, начинается HITL — **раунды формы**
(`microfluidics/tz_review.py`, `TZSessionAgent._review_decision`):

1. Панель открывается сама, в чате появляется карточка «Проверка ТЗ —
   раунд N» с кнопкой «Открыть ТЗ». **Сверху** — разделы, где есть поля
   «не задано» («ожидают заполнения человеком»), с вопросом и подсказкой из
   опросника VibePAV; **ниже** — заполненные разделы по возрастанию номера.
   Как только в разделе заполнены все пустые поля и фокус уходит из него,
   раздел перемещается вниз на своё место (и обратно, если поле очистить).
2. Любое поле можно исправить. Введённое значение → «уточнено оператором»
   (этот статус — только за правками человека; значения, которые агент
   постановки ТЗ подобрал сам, приходят со статусом **«автоподбор»**).
3. **Поле можно оставить пустым.** Кнопка ⊘ справа от поля (или «Не
   заполнять пустые» внизу — отмечает все пустые поля разом, отправка
   по-прежнему основной кнопкой) переводит поле в статус **«не требуется»**:
   параметр намеренно без ограничения, агент его не дозаполняет, следующие
   агенты не используют его как критерий, в документе он в разделе свободных
   полей. Той же кнопкой убирают лишние значения, которые подставил агент;
   ↺ на её месте возвращает поле (с прежним значением).
4. **Поле, оставленное пустым, заполняет агент**: он получает список таких
   полей и заполняет их тулом `fill_agent_fields(section, fields)` — по
   разделу за вызов, с прогрессом и точными ошибками, как `fill_tz_section`.
   Статус — **«заполнено агентом»**.
5. ТЗ снова приходит оператору (раунд N+1): поля агента **выделены жёлтым**
   с пометкой «проверьте значение агента». Оставил значение — статус
   сохраняется, исправил — «уточнено оператором», очистил — агент заполнит
   снова, ⊘ — «не требуется». Раунд, в котором не осталось пустых полей («Подтвердить ТЗ»),
   согласует ТЗ; дальше документ публикуется, и пайплайн идёт дальше.

Застрять нельзя: не больше 5 раундов на запрос; без ответа (таймаут) ТЗ
принимается как есть — поля «не задано» остаются открытыми, агент ничего не
выдумывает без человека. Для формы таймаут авто-подтверждения не меньше
30 минут (`HITLRequest.timeout_seconds`; `WebHITLHandler` продлевает, но
никогда не сокращает общий таймаут). Консольный обработчик форму не
показывает: «Approve» принимает ТЗ как есть, «Edit» с текстом — полное
перезаполнение с раздела 1.

**Диагностика, если вопросы «не приходят».** Откройте
`GET /api/hitl-status` — там видно: включён ли HITL, привязан ли websocket,
какие агенты подключены и какие запросы ревью ждут ответа. Жизненный цикл
каждого запроса пишется в `logs/app.log` (логгер `CoScientist.web.hitl`):
отправка в браузер, ответ или `HITL TIMEOUT … AUTO-APPROVING` (через 300 с без
ответа пайплайн продолжается автоматически — об этом придёт системное
сообщение в чат). При переподключении вкладки неотвеченные запросы ревью
доставляются повторно; страница отдаётся с `Cache-Control: no-store`, чтобы
браузер не держал старый фронтенд. После обновления кода перезапускайте сам
процесс сервера — кнопка Stop в UI сбрасывает только сессию, не код.

**Отключение для тестирования без человека** — один переключатель:

```bash
HITL__ENABLED=false            # env или .env — циклы ревью проходят насквозь
python scripts/run_microfluidics_web.py --no-hitl   # то же самое для веба
```

Точечно HITL отключается на конкретном агенте через `hitl: false` в
`microfluidics.yaml`.
