## 1. Площадка: AAAI-27 Demonstrations

Call: https://aaai.org/conference/aaai/aaai-27/demonstration-call/

**Сроки**
- Приём статей: **18 сентября 2026, 23:59 AoE (UTC-12)**.
- Решение: 6 ноября 2026.
- Camera-ready: 20 ноября 2026.
- Демонстрации на конференции: 18–21 февраля 2027.

**Формат**
- 2 страницы в двухколоночном шаблоне AAAI плюс 1 страница ссылок.
- В тексте должны быть технические детали, related work и значимость демонстрации.
- Работа не должна быть опубликована ранее. При принятии права передаются AAAI.
- Можно single-blind или double-blind.

**Видео**
- До 5 минут, загружается как supplementary в OpenReview.
- Весит больше, чем подача только со слайдами.
- Первые 30–60 секунд организаторы советуют отдать на обзор.

**Необязательно:** код в supplementary (приветствуется), открытый код, чеклист воспроизводимости.

**Критерии оценки:** ясность, значимость демонстрации, интерес для AI-сообщества, способность увлечь аудиторию, новизна.

**Участие в конференции**
- Хотя бы один автор каждого демо регистрируется и приезжает.
- Стенд: монитор, стол, розетка, постер.
- Нужен запасной режим без особого оборудования.
- Лучшее демо получает награду по оценкам аудитории и рецензентов.

## 2. EMNLP 2026 Demo: что сказали рецензенты

Submission 241, «Alembic: Autonomous Synthesis of MCP Servers from Scientific Repositories».

- **Решение:** Reject. AC ZpCS рекомендовал отклонить, confidence 4.
- **Reviewer fhxJ:** 6 (marginally above), confidence 4.
- **Reviewer QhoV:** 4 (ok but not good enough), confidence 3.

**Что хвалили оба рецензента**
- Законченный пайплайн, зрелый артефакт, удобный интерфейс, развёртываемый результат.
- Открытый код, скринкаст и веб-демо, воспроизводимость.
- Текст («exceptionally well-written»), принцип «LLM proposes, code disposes», таблица сравнения, кейс MedSAM.
- Раздельные окружения (репозиторий на своём интерпретаторе, сервер на современном Python). QhoV назвал это новым и практически полезным решением.

**Слабые места.** Первые три AC назвал главными.

1. **Самопроверка.** Explorer выводит спецификацию, Coder пишет код и тесты, Validator проверяет теми же данными. Неверное понимание репозитория даёт согласованные неверные код и тест. Гейты проверяют структуру (символ существует, компиляция, импорт, запуск), семантику они не проверяют. На внешних тестах TM-Bench результат ниже. AC: «More importantly, the validation process is partly self-referential».
2. **Сравнение на разных моделях.** Alembic работал на GLM-5.2, ToolMaker взят из статьи на GPT-4o. Итог при этом ниже: 27/42 против 37/42 вызовов, 93/124 против 116/124 тестов. Аннотация утверждала «matches or exceeds».
3. **Known-target режим.** Системе сообщали нужный инструмент, поэтому автономное обнаружение инструментов не проверено.
4. **Нет абляций.** Не показано, зачем пять агентов и четыре гейта и справится ли один агент. Нет базовой линии в виде Claude Code, Codex CLI или CodeBuddy с простым промптом.
5. **Токены.** 37 млн против 7,9 млн, в 4,7 раза больше. Расход по стадиям не разобран.
6. **Узкий домен.** Почти все 14 репозиториев из биомедицины.
7. **Поверхностный разбор отказов.** «Other» 8 из 30 runtime-ошибок, причины 4 abort в Environment не разобраны.
8. **Удобство инструментов.** Качество имён, документации и обработки ошибок никто не проверял на людях или агентах.

**Вывод для следующих подач.** Статус demo не помог, утверждения о надёжности судили как в исследовательской статье. Заявлять можно только то, что закрыто данными.

## 3. Черновик AAAI-27 Main: что из него берём

Файл `papers/aaai27-main-draft/OUTLINE.md`. Статья переписана после честных прогонов:

- Alembic как experiment module общей AI4Science-системы (CoScientist: planner → action graph → executor). Его задача: наращивать проверенный переиспользуемый каталог инструментов.
- По точности на отдельной задаче современные coding-агенты не хуже. Ценность Alembic в каталоге: воспроизводимые повторные вызовы, покрытие произвольных репозиториев, стоимость конверсии делится на многие вызовы.
- Начинать с воспроизводимости. Стоимость вызовов модели быстро падает, и довод «дешевле» легко оспорить.
- Главный риск по новизне: Paper2Agent, ToolMaker и ToolUniverse уже превращают репозитории и статьи в MCP. Отличие, которое можно отстоять: система, использующая растущий каталог в разных исследованиях.
- Гибридная схема: сперва каталог, coding-агент при отсутствии инструмента.
- Раздел ограничений остаётся: точность на уровне coding-агентов, дрейф контракта редок, современные агенты сами неплохо ставят окружения.

Каскад local → hub → build из ветки `alembic-mcp-hub` реализует шаг «reuse или build» из раздела 3 outline.

## 4. TM-Bench: честные цифры на одной модели

В EMNLP Alembic уже работал на GLM-5.2. Неравные условия были только у ToolMaker (GPT-4o из статьи). ToolMaker позже перезапустили на `openrouter/z-ai/glm-5.2`.

| | Тесты gold | Задач целиком | Условия |
|---|---|---|---|
| Alembic, GLM-5.2 | 93/124 | 9/15 | один прогон без перезапусков, 10–11 июля, gold до исправления pathfinder |
| ToolMaker, GLM-5.2 | 122/124 → 124/124 | 15/15 | 19 июля; повторы на 4 задачах, ручные правки на 2, gold pathfinder исправлен |
| ToolMaker, GPT-4o (из статьи) | 116/124, 37/42 вызовов | | цифры, которые были в EMNLP |

**Alembic по задачам**
- **Прошли целиком (9):** conch, musk, stamp_extract, uni, medsam, cytopus, esm, modernbert, tabpfn.
- **Частично:** nnunet_train_model 2/4, pathfinder_verify_biomarker 4/6.
- **Ноль:** flowmap, medsss, retfound, stamp_train_classification_model.

**Условия прогона ToolMaker** (`benchmarks/toolmaker-glm52/summary_final.tsv`)
- **Повторы:** flowmap и medsss упали дважды и прошли с третьей попытки. У modernbert и uni отдельно перезапускали create.
- **Ручные правки:** в nnunet_train_model поправлен `code.py` (`-np 2`, свой trainer без валидации). В stamp_train_classification_model поставили `cores=2` и monkeypatch через `sitecustomize.py`.
- **Gold pathfinder:** в yaml колонки OS заменили на DSS (эталонные p-value считались по DSS). Alembic оценивали до правки, его 4/6 могут частично объясняться этой ошибкой в gold.

Сколько ToolMaker набрал бы с первой попытки без правок, без пересчёта сказать нельзя. Решено не пересчитывать.

**Что нужно для честного сравнения, если когда-нибудь дойдут руки:** переоценить Alembic по исправленному gold и дополнительно одно из двух, либо дать обеим системам одинаковое число попыток, либо взять у ToolMaker результаты первой попытки без ручных правок. Для статьи цифры нужны в сжатом виде, места мало.

**Формулировка для статьи**
> On the same GLM-5.2 model, a single unattended Alembic run passes 93 of 124 TM-Bench gold tests (9 of 15 tasks); ToolMaker reaches 124 of 124 after retries on four tasks and manual code fixes on two.

**Собственные метрики Alembic** (`benchmarks/alembic_selfmetrics_v2.md`): 77 инструментов, 67 passed, 35 perfect. Их считают наши же тесты. Это ровно то, что рецензенты назвали самопроверкой, поэтому ведущим доводом в статье они быть не могут.

## 5. Что сделано после EMNLP

**Хаб на Docker Hub**
- Namespace `peanutbuttermilk`, репозитории `alembic-tool-<repo>`, теги `<job_id>` и `latest`.
- Метаданные сборки (JSON с числом инструментов) хранятся в полном описании репозитория.
- Загрузка вручную или автоматически после сборки. Автозагрузка не заменяет на хабе лучшую сборку (сравнение по passed, затем perfect). Кнопка ручной отправки заменяет всегда.
- Страница Hub в веб-интерфейсе: поиск, теги, Pull & start.

**Переиспользование**
- Агент ищет сервер локально, затем в хабе, и только потом конвертирует репозиторий.
- Стабильный перезапуск ранее собранных серверов.
- Ручной Run в интерфейсе всегда собирает заново и не обращается к хабу.

**Валидация**
- Каждый вызов валидатора записан в `validation.json`: аргументы и результат.
- Debugger сохраняет пример аргументов, только если инструмент с ними вернул результат. Файлы примеров лежат в `output/samples/`.
- Параметры инструментов только JSON-совместимые. Результаты pandas и numpy отдаются как JSON.

**Интерфейс**
- Диалог пересборки с подсказкой и описанием задачи.
- Просмотр файлов из S3, таблицы и SVG.
- История вызовов инструментов.
- Удаление только контейнера или образа целиком.

**End-to-end сценарии** с CoScientist работают.

## 6. Кейс: рецептуры резины для шин

### Постановка (переписка с Глебом, `discussion/engineering_case.md`)

У производителей шин свои рецептуры резины, и ими не делятся. Отстающие производства восстанавливают состав реинжинирингом: разбирают готовую шину. Есть несколько полузаброшенных репозиториев с расчётными методами, которые якобы подбирают состав под нужные свойства. Раньше Наргиза пробовала их запускать, и часть не заработала.

**Идея Глеба:** прогнать этот путь через CoScientist.
- Сформулировать инженерную гипотезу: по коду и расчётам можно построить метод разработки рецептуры.
- Найти литературу и репозитории, собрать их через Alembic и проверить, что работает.
- Отчитаться, что работает, что нет и что можно связать.

Отрицательный итог допустим. Результат: проведённое исследование, граф исследования и хаб рабочих инструментов, от которых можно продолжать. Цель: воспроизвести работу Наргизы системой и сохранить сессию. Если просто дать в промпт список ссылок на репозитории, это тоже годится. Если система сама найдёт дополнительные инструменты, ещё лучше.

**Статус реального проекта.** НДА с заказчиком (Татнефть) не подписан, проект не стартовал, данных заказчика нет. Наргиза получила от Глеба тестовое задание: запустить найденные модели, особенно генеративные, и посмотреть, с какими объектами они работают. Потом ей предложили два пути, исследование по открытым данным о резиновых смесях или работа с CoScientist (тестирование и правка багов). Она выбрала работу с CoScientist и параллельно поиск моделей с проверкой на собранном датасете.

**Организационное из переписки**
- Глеб предлагает позвать Наргизу в соавторы.
- Рабочее название идеи: AI for Engineering.
- Дата, которая звучала в переписке: хорошо бы успеть до 28 сентября. К дедлайну AAAI-27 Demonstrations (18 сентября) она отношения не имеет.
- Глеб: кейс выглядит мощно даже для демо, можно стартовать с демо, а подробное описание архитектуры CoScientist вынести в отдельную статью.

### План проекта (`tyre-case/project_plan_gdoc.txt`)

**Цель проекта.** Иерархический каскад из трёх forward-моделей по стадиям производства:
1. **Смешение:** сырьё и режим → Муни сырой смеси, дисперсия наполнителя.
2. **Вулканизация:** рецептура и режим → реометрия (ts2, t90, MH, ML).
3. **Вулканизат:** реометрия и рецептура → прочность, удлинение, твёрдость.

**Зачем каскад**
- Меньше итераций «синтез → испытание».
- Дорогие тесты (DMA, износ) заменяются прогнозом по дешёвым (Муни, реометрия).
- SHAP-объяснения.
- Основа для обратной задачи: поиск рецептуры под баланс свойств многокритериальной оптимизацией (NSGA-II/III, Bayesian MOO) по «магическому треугольнику» rolling resistance, wet grip, износостойкость.

**Ограничение.** Исторических рецептур мало. Отсюда дескрипторы сырья, SMILES, transfer learning и аугментация генеративными моделями с лабораторной проверкой.

**Способы представления компонентов**

| Способ | Что это | Что «понимает» модель |
|---|---|---|
| Состав в phr | одно число на компонент | только количество, новый компонент = новая колонка |
| Дескрипторы партий | параметры входного контроля | вариабельность сырья |
| RDKit-дескрипторы | ~200 характеристик молекулы | общая химическая природа |
| Морган-фингерпринты | бинарный вектор 1024/2048 | конкретные фрагменты |
| GNN | молекула как граф | структура, перенос на новые молекулы |
| Эмбеддинги (polyBERT, ChemBERTa) | вектор от предобученной модели | лучший перенос на новые компоненты |

**Гипотезы этапа 1**
- H1: дескрипторы входного контроля дают ≥3% R² к модели только на phr.
- H2: каскад из трёх моделей лучше монолитной модели.
- H3: молекулярные представления повышают точность на редких компонентах.
- H4: удаление систематических выбросов (5–10%) даёт больше, чем смена алгоритма.
- Отдельно: можно ли посчитать целевые свойства найденными расчётными методами.

**Этапы**
- **Месяцы 1–3:** аудит данных, baseline XGBoost/LightGBM по трём ступеням с четырьмя вариантами признаков, SHAP, проверка гипотез, Gate 1.
- **Месяцы 4–6:** нейросети и GNN, transfer learning, аугментация (VAE, физические правила Fox и Mark–Houwink, дезагрегация по партиям), лабораторная проверка синтетических точек, слепой тест на 5–10 рецептурах, анализ окупаемости.

### Кодировки, которые разобрала Наргиза

**polyBERT.** На входе pSMILES, на выходе вектор из 600 чисел.
- PS: `[*]CC([*])c1ccccc1` → `[0.3508118 0.11451036 0.38645813 ...]`
- BD: `[*]=CCCC=[*]` → `[0.13955462 0.37534162 -0.6360624 ...]`
- Смесь кодируется средневзвешенным по долям: для PS 25% и BD 75% первый элемент `0.25 * 0.3508 + 0.75 * 0.1396 = 0.1924`. Итог тоже 600 чисел: `[0.19236892 0.3101338 -0.38043225 ...]`.

**PolymerGNN.** Вход похож на phr, только в молях:
```
Resin#,Reactor,AN,OHN,IV,Tg,Mw (PS),%IPA,%1,4-CHDM,%TMP
1,Kettle,4.5,19,0.279,81.65,24619,49.8,59.1,0.8
```
Из строки выделяются спирты и кислоты, строятся графы мономеров и добавляются свойства (молекулярная масса и др.). На выходе суммарный вектор из 68 чисел.

**Остальные работы**
- Hu et al.: VAE учится на 3 физических параметрах из симуляции (массовая доля белков и две силы взаимодействия) и генерирует точки в этих координатах.
- Wan MT-DNN и Wan CJPS: табличные векторы из параметров процесса (время, температура, режимы) и дескрипторов дисперсии и типов каучука.
- Choudhury: обычный phr-вектор.
- Soft sensor: временные ряды с температурой, давлением и мощностью мотора.

Когда в работе встречаются Муни или реометрия, рецептура обычно кодируется в phr хотя бы на входе.

## 8. Решения

1. **Главное демо: одна статья по схеме Глеба.** Архитектура исследования CoScientist с Alembic как модулем экосистемы инструментов, кейс с шинами, хаб. Критерии трека (значимость, интерес аудитории, новизна) этой схеме подходят.
2. **Второе демо про Alembic и хаб допустимо** при трёх условиях:
   - **разные вклады:** в главном демо Alembic занимает один абзац, второе демо описывает Alembic и хаб как инструмент для разработчиков AI4S-систем, без кейса и без CoScientist;
   - **без сравнительных утверждений:** убрать «matches or exceeds», «correctness by construction», «eliminates whole classes of failure», вместо «verified» писать «inspectable»;
   - **подробности в препринт:** внутренности Alembic выносятся на arXiv.

   Цена второго демо: сокращённый текст, новый раздел про хаб, отдельное видео и отдельный стенд в феврале.
3. **Технический препринт на arXiv.** Полная EMNLP-версия с хабом, каскадом, историей валидации и честными цифрами на одной модели. Обе демо-статьи ссылаются на него. Препринт не нарушает «previously unpublished» для демо: отклонённая EMNLP-статья не опубликована.
4. **Анонимность: single-blind для обеих статей.**
   - Хаб, репозиторий, скринкаст и HF Space раскрывают авторов, поэтому double-blind для демо почти невыполним.
   - Смешивать режимы бессмысленно: открытая статья раскроет анонимную через общий хаб.
   - В single-blind статьи ссылаются друг на друга как concurrent submission или через arXiv.
   - Статья Вани цитируется обычным образом.
5. **TM-Bench в главном демо:** одно предложение из раздела 4 в конце раздела о системе.
6. **Хаб:** 14 серверов, без слова «огромный».

**Черновик abstract (англ.)**
> Large language model systems can now carry out separate stages of scientific and engineering research, yet the code, environments, and intermediate results they produce rarely outlive the session that created them. We present an AI-for-Science architecture that couples the CoScientist research system with Alembic, a module that converts scientific repositories into validated Model Context Protocol servers and shares them through an open Docker Hub catalogue. The research agent looks for a tool locally, then in the hub, and converts a repository only when neither has it. Each conversion keeps the environment, the tool code, and the history of validation calls needed to run it again.
